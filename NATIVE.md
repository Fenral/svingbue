# Flightglass — native packaging and release

Flightglass uses the same static source in two deliberately separate ways:

1. Vercel builds and serves the explicit allowlisted `www/` artifact at
   `https://svingbue.vercel.app`; it never publishes the repository root.
2. Capacitor packages that same allowlisted artifact as the native app. Codemagic
   generates, signs and uploads the iOS project on a cloud Mac.

Protected release identity:

- App ID: `no.strikearc.app`
- App name: Flightglass
- App Store Connect Apple ID: `6768449250`
- Apple Team ID: `PL9G26C26C`
- App Store Connect integration: `ryddy-asc-key` (Key ID `JQVPW4D944`)
- Minimum iOS version: 16.4
- Device family for v1: iPhone only

The existing App Store record is retained. Changing the public store name and
metadata is an App Store Connect task; it does not require a new bundle ID.

## Clean native payload

`scripts/copy-web.mjs` creates a disposable `www/` directory containing only
the v1 app:

- Home: `index.html`
- Range/Outcome replay: `impact.html`
- Mechanics Lab: `impact-studio.html` (internal route id `studio`)
- Flightglass Guide: `jarvis.html`
- Support: `support.html`
- Terms and Privacy
- required top-level modules/styles plus an explicit allowlist from `vendor/`
  and `assets/`

Academy v2, Geometry/`geo3d`, Three.js, historical mocks and development
tooling are denied. `www/` is gitignored and recreated on every run. Capacitor
and Vercel both point only to `www/`; `vercel.json` enforces the web boundary.

`support.html` is the public support destination for App Store and Google Play
listings. It also remains available locally in the native payload so users can
reach the same support guidance without depending on a network request.

## Why `ios/` is not committed

The development machine is Windows. The `ios/` project requires Xcode and is
therefore regenerated by Codemagic for every build:

1. Install pinned npm dependencies and run the v1 source/release contracts.
2. Create `www/` and inject the iOS RevenueCat public SDK key into that
   disposable copy.
3. Run `npx cap add ios` and `npx cap sync ios`.
4. Patch the generated project for iPhone-only v1, portrait-first shell
   behavior, Mechanics portrait/landscape support, full-screen display, the
   Flightglass display name and iOS 16.4. Mechanics releases the route-level
   orientation lock; it never shows a forced-rotate overlay.
5. Set the export-compliance answer and generate icon/splash assets from
   `resources/`.
6. Install CocoaPods, set marketing/build versions, apply persistent signing,
   archive the IPA and upload it to TestFlight.

The `ios-testflight` workflow is manual-only. A push to `main` does not start
or authorize an iOS upload.

## RevenueCat configuration

The committed source intentionally contains placeholders in
`sa-iap-config.js`. Public RevenueCat SDK keys are application identifiers, not
secret API credentials, but a native build must still fail closed if the
correct project key is absent.

The public SDK key is not the Apple store credential. Flightglass currently
uses Capacitor Purchases 11.x, so the RevenueCat App Store app also requires an
active Apple In-App Purchase Key (`.p8`) plus Key ID and Issuer ID. Generate or reuse the
key under App Store Connect → Users and Access → Integrations → In-App
Purchase, upload it only in RevenueCat, and require RevenueCat's credential
validator to show valid. Never copy that `.p8` key into Codemagic variables,
the app bundle or Git.

For iOS:

1. Create a Codemagic environment group named `revenuecat-flightglass`.
2. Add `REVENUECAT_IOS_PUBLIC_SDK_KEY` with the Flightglass public iOS SDK key
   beginning `appl_`.
3. Keep the real value out of Git.
4. After `npm run copy-web`, run `npm run configure:iap:ios` and
   `npm run verify:iap:ios`. These commands write and validate only
   `www/sa-iap-config.js`.

For a later Android release, use `REVENUECAT_ANDROID_PUBLIC_SDK_KEY` beginning
`goog_` with the equivalent Android commands. The current Android workflow
produces only a development APK, not a Play release.

The protected product contract remains:

- `strikearc_pro_monthly`
- `strikearc_pro_annual`
- `strikearc_pro_lifetime` — restore compatibility only
- RevenueCat entitlement: `pro`

## Signing contract

Flightglass must use one reusable Apple Distribution certificate and a
matching `IOS_APP_STORE` provisioning profile for `no.strikearc.app`.
Automation must import or fetch that persistent identity on each run. It must
not revoke team-wide certificates, and it must not create a fresh distribution
certificate for every build.

The App Store Connect API integration is already named in `codemagic.yaml`, but
the certificate/profile still need to be proven on a successful archive. Treat
signing as open until a manually triggered build signs and uploads successfully.

## Build and version contract

- The marketing version is read from `package.json` (currently `1.0.0`). Before
  building, confirm that this version train is available on the existing App
  Store record.
- The build number is one above the latest TestFlight build returned by App
  Store Connect.
- If the latest build number is missing or non-numeric, the workflow fails. It
  must never silently fall back to build 1.
- Xcode is pinned to 26.6 so the archive uses Apple's required iOS 26 SDK.
- `scripts/generate-ios-assets.mjs` reads only `resources/icon.png` and
  `resources/splash.png`; `scripts/verify-generated-ios-assets.mjs` then checks
  the generated dimensions and pixels before signing.

## Manual TestFlight run

Start `ios-testflight` in Codemagic only after all of these are true:

- the GitHub release gate is green on the exact commit;
- `revenuecat-flightglass` supplies a valid iOS public SDK key;
- RevenueCat validates the Apple In-App Purchase Key and Issuer ID;
- Monthly and Annual exist in App Store Connect and the current RevenueCat
  Offering grants `pro`;
- legacy Lifetime still grants `pro` for existing-owner restore;
- Paid Apps Agreement, tax and banking are active;
- persistent signing is available;
- the `1.0.0` App Store version train is confirmed or deliberately updated;
- store metadata, privacy declarations, review notes and screenshots are ready;
- the repository's release authorization conditions are satisfied.

After upload, do not submit for App Review until a native sandbox build proves:

- one Monthly or Annual purchase;
- cancellation/error behavior;
- Restore Purchases;
- restoration of an existing Lifetime entitlement;
- core Home, Range/Outcome, Mechanics and Guide flows on a physical iPhone,
  including Mechanics in portrait and landscape.

TestFlight in-app purchases use Apple's sandbox environment. Restore Purchases
must be initiated by the user from Home or the paywall; it must not run
automatically on launch.

See `docs/app-review-notes.md` for reviewer copy and
`docs/store-listing.md` for listing metadata and account-level declarations.

## Android track

`.github/workflows/android-debug.yml` regenerates Android, applies the native
orientation compatibility contract, generates assets from `resources/` and
uploads an unsigned debug APK. Home, Range/Outcome and Guide stay portrait-first;
Mechanics releases its route lock for portrait or landscape. A production Play release additionally requires
a protected upload key, signed AAB, Play Console listing/data-safety form,
RevenueCat Android project/product mapping and a chosen release track. None of
those external assets should be inferred from a green debug build.
